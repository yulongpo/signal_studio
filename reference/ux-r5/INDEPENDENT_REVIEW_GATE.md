# UX-R5 独立审核与远端发布门禁

## 1. 不可绕过的原则

- **开发 Agent 不得自审、不得伪造子代理报告**；必须由没有参与本次实现与修复的独立 Review 子代理阅读实现、变更、原始测试和实际 Qt 运行证据。
- 任意阶段允许本地 `git commit`，但审核前**绝对禁止 `git push`、创建远端分支、更新远端 ref、触发带远端写入的发布脚本**。
- 审核对象是最终精确 Git HEAD，而不是“近似同一文件树”、开发者总结、合成 HTML 原型或旧分支审核结果。
- 若环境不支持真正独立子代理，则最终标记 `BLOCKED`，保留本地代码，不得由主 Agent 代签并推送。

## 2. Reviewer 工作边界

### 必审

1. 读取 `PLAN.md`、`ACCEPTANCE_MATRIX.md`、最终 diff、核心服务层和持久化代码；检查是否有未解释的需求偏差。
2. **服务层只读不变量**：导入标签/算法结果不能被任何写 API 改动（含 `reviewBatch`、`deleteBatch`、`rename`、几何和段管理）；仍可选中、定位和导出。
3. **转换事务**：单项/批量独立副本，来源几何语义、未知时间、来源证据、重复控制、撤销/重做，原来源不变。
4. **正式检测结果唯一性**：成功新结果、零结果、失败、取消、ROI、样本通道切换、文件切换、重开、崩溃点与旧资产回收；退役结果不能从历史扫描复活。
5. **窄带通道**：既有通道创建快照不丢失，旧检测来源退役后仍能定位来源文件并明确标注绑定状态；不静默重绑到其他信号。
6. **跨视图选择**：Tab、工程树、图谱和右侧属性不混淆对象 ID；图谱层可见性与表格内容浏览行为符合设计。
7. **原生界面**：真实 Qt 运行、按钮可用性、只读控点无拖动、单/多选转换和更新状态；高 DPI、窄侧栏文字无交叠。
8. **证据完整性**：任务日志、实际失败/跳过说明、工程重开与崩溃恢复记录，不把代码静态检查当成实际原生验证。
9. **SHA 最小化**：不得运行全库/大素材目录 hash 盘点；产品自身存储/模型校验保持正确。

### 禁止

- Reviewer 不得写入正在审核的产品源码、测试或生成新代码来使其通过。
- Reviewer 不得自行推送或改变分支 HEAD。
- Reviewer 不得用“文档声称全部通过”代替复核实际证据。
- Reviewer 若发现阻断问题，只报告 `REJECTED` 和可复现证据；主 Agent 修复并重新提交后，需要重新审核**新 HEAD**。

## 3. 建议报告格式

以下报告应写至**仓库外**可交付路径（例如 `out/tasks/ux-r5/INDEPENDENT_REVIEW.md`），而非在审核结束后新增一个改变被批准 HEAD 的提交。若必须将报告纳入版本库，应通过后续完整再审重新绑定新 HEAD。

```markdown
# UX-R5 独立终审
Decision: APPROVED | REJECTED | BLOCKED
Reviewed-HEAD: <full Git commit id>
Reviewer: <独立子代理身份及运行方式>
Date: <日期和时区>

## 独立性
<与主实现/修复隔离的具体依据>

## 检查清单
| 项目 | 证据路径 | 结果 |
|---|---|---|
| 服务层只读 | ... | PASS/FAIL |
| 单批转换与撤销 | ... | PASS/FAIL |
| 检测整体替换/零结果 | ... | PASS/FAIL |
| 恢复与资产清理 | ... | PASS/FAIL |
| 通道快照与旧工程 | ... | PASS/FAIL |
| Qt 原生与布局 | ... | PASS/FAIL |

## 不通过/遗留问题
<Blocker/Major/Minor、可复现步骤、风险及最终判决依据>
```

## 4. 审核通过后的安全同步

1. 主 Agent 读取并校验 `Decision: APPROVED` 和 `Reviewed-HEAD` 与当前本地 `HEAD` **完全一致**。
2. 运行一次必要的 `git status --porcelain`，确认跟踪文件无未提交改动；检查远端连接和目标分支最新 HEAD 与本地祖先关系。允许读取 Git 提交 ID，**不做整仓 SHA-256**。
3. 若远端新增提交：先安全 fetch、整合/变基（视仓库保护策略），补跑受影响验证，**再次由独立 Review Agent 审核新的 HEAD**；不能拿旧 `APPROVED` 直接推。
4. 仅在远端是待推送 HEAD 的祖先且分支受保护规则允许时，执行**非强制**的定向推送，例如 `git push origin HEAD:refs/heads/rebuild/a143-native`。
5. 推送后读取一次远端分支 HEAD，确认为目标版本；将结果写到仓库外发布记录。禁止 `--force`、`--force-with-lease`，禁止绕开审核发送其它远端写入。
6. 若远端权限失败，记录 `SYNC_BLOCKED`，保留本地结果，绝不声称同步成功。

## 5. 合理的 SHA 开销边界

- 允许：`git rev-parse HEAD`、`git merge-base --is-ancestor`、必要的 `git fetch`、产品代码本身既有的模型/源资产完整性校验。
- 禁止：逐文件 `sha256sum` 全仓扫描、多轮重复生成二进制/截图/报告 hash 清单，为报告而计算大模型/大 IQ 文件完整指纹。
- 对于检测资产，优先复用既有 `detection_store` 持久化完整性 API 和轻量 manifest；**绝不能借“减少 SHA”取消生产完整性安全约束**。
